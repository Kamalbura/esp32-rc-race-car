# Harden ESP32-S3 RC control first

## Executive summary

The rc-cyber-truck V2 design is ahead of most hobby ESP32 RC projects on link safety: it already combines encrypted ESP-NOW unicast, fixed-channel operation, PMK/LMK keys, bounded packets, CRC, session IDs, sequence checks, a kill control, a 120 ms receiver failsafe, telemetry acknowledgements, and transmitter send gating. Its main weakness is not the radio choice; it is the boundary between the Wi-Fi callback, application state, and motor-control safety. The next release should move packet validation and state commits out of callbacks, make session persistence and callback timeout handling generation-aware, add an independent task watchdog and startup inhibit, and test loss, replay, reboot, and rollover faults on a real vehicle.

Compared with similar GitHub projects, rc-cyber-truck has the strongest protocol foundation but lacks their most valuable missing evidence: encoder-closed-loop control, current/stall protection, measured latency distributions, stop-distance tests, and host-side fault-injection tests. Current Espressif practice supports ESP-NOW for low-latency control, queue-based callbacks, disabled sleep for an always-on link, capability-aware memory allocation, ESP-NN/ESP-DSP/TFLite Micro/ESP-SR, and camera buffers in PSRAM. The 2 MB PSRAM/8 MB flash remote can support the radio UI, telemetry, IMU filtering, light DSP, and one small voice/classification workload. The 8 MB PSRAM/16 MB flash car can add camera buffers, audio, logging, and modest INT8 vision, but not high-rate modern object detection or an AI-controlled safety loop. Firecrawl was unavailable; this report uses the supplied project notes plus available official Espressif documentation, GitHub repositories, and direct web sources.

## The project is protocol-strong but not yet test-strong

The repository’s V2 protocol is a sensible safety baseline. A 10 ms control period gives a 100 Hz command rate, the 120 ms receiver timeout limits command age, and the kill path bypasses the motor ramp. Session IDs, modular sequence checks, exact-size/version checks, CRC-16/CCITT, source-MAC filtering, safe-start centering, and telemetry sequence acknowledgements address common accidental and stale-packet failures. The encrypted-unicast design is materially stronger than broadcast or a shared token: Espressif documents CCMP protection for ESP-NOW unicast, 16-byte PMK/LMK keys, and a maximum peer count that is configuration-dependent ([ESP-NOW security and peer limits](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/api-reference/network/esp_now.html#security)).

Those protections do not make ESP-NOW an application protocol by themselves. Espressif explicitly says a successful send callback indicates MAC-layer delivery, not that the application accepted or acted on the command; applications needing that guarantee should add an application ACK and sequence handling ([send semantics](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/api-reference/network/esp_now.html#send-esp-now-data)). The official example adds type/state/sequence/CRC/magic fields and queues callback events for lower-priority processing ([official example](https://github.com/espressif/esp-idf/tree/master/examples/wifi/espnow)). Therefore, the project’s `sequenceAck` should be described as “receiver acted on sequence N,” while the send callback should be exposed separately as “MAC send succeeded.”

The most important implementation issues are tightly coupled to that distinction. The receiver currently performs MAC, length, version, CRC, timing, and state work in the receive callback. The first accepted session is not persisted through the same pending-session path as a later session change. On the transmitter, the 50 ms callback recovery timeout can allow a late callback from an expired transmission to mutate send-gate state. None of these necessarily fails during normal operation, but each creates an edge case under RF loss, reboot, or callback reordering. Espressif warns that Wi-Fi callbacks run in a high-priority task, should remain short, and should hand work to a queue ([receive-callback guidance](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/api-reference/network/esp_now.html#receiving-esp-now-data)).

The 120 ms failsafe is a reasonable starting engineering value, not a certified racing limit. It must be validated against speed, drivetrain braking, tire grip, RF burst loss, and UI jitter. A one-second timeout appears in [Deejpotter’s ESP-NOW car](https://github.com/Deejpotter/esp32-wireless-car), while [vitorccs’s S3 camera car](https://github.com/vitorccs/esp32s3cam-rc-car) sends commands every 50 ms and stops when the watchdog expires. Those projects demonstrate the pattern, not a safe value for this vehicle. The project should measure command age, stop distance, and worst-case callback latency before tightening or loosening the bound.

Across these projects, the largest unclaimed opportunity is closed-loop vehicle control. None of the surveyed repositories publishes a reproducible encoder calibration, speed-tracking error, latency distribution, or stopping-distance benchmark. rc-cyber-truck should make those measurements a first-class artifact rather than adding another UI feature.

## Espressif practice defines a safe partition between control and compute

Espressif’s current stack makes the ESP32-S3 a capable companion computer, not a small autonomous-driving computer. [ESP-NN](https://github.com/espressif/esp-nn) reports roughly 54 ms INT8 person detection in one optimized setup, but approximately 729 ms for MobileNetV3 Small and 1,253 ms for YOLO11n at the cited configurations. These are inference times, not camera capture, preprocessing, queueing, or actuator latency. [ESP-DSP](https://github.com/espressif/esp-dsp) supplies vector math, filters, FFTs, and Kalman APIs; [Espressif’s TFLite Micro component](https://github.com/espressif/esp-tflite-micro) supports small INT8 models; [ESP-SR](https://github.com/espressif/esp-sr) supports wake-word and command recognition; and [esp32-camera](https://github.com/espressif/esp32-camera) recommends JPEG and PSRAM for larger frame buffers.

The correct architecture is therefore deterministic control plus best-effort observers. The motor-enable/failsafe path, latest validated command, timeout bookkeeping, watchdog service, encoder/IMU interrupt shims, and small queues belong in internal RAM/IRAM where required. Camera JPEG buffers, tensor arenas, audio rings, telemetry history, and noncritical UI assets can use PSRAM. ESP-IDF documents that PSRAM is cache-mediated and that flash operations can suspend cache access; an ISR or safety path cannot assume PSRAM or flash has deterministic availability ([external RAM](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-guides/external-ram.html), [memory types](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-guides/memory-types.html), [flash concurrency](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/peripherals/spi_flash/spi_flash_concurrency.html)).

### Realistic capacity by board

| Board configuration | Realistic workload | Do not promise |
|---|---|---|
| **Remote: 8 MB flash / 2 MB PSRAM (N8R2 shorthand)** | Encrypted ESP-NOW, joystick/display, telemetry, IMU yaw-rate display, complementary/Kalman filtering, FFT diagnostics, local history, and one small WakeNet or command/classification model. A single low-resolution JPEG snapshot is plausible as a diagnostic feature. | Continuous camera inference alongside a strict 100 Hz transmitter deadline; large dual-OTA plus multiple model assets without a carefully designed partition table; PSRAM as real-time SRAM. |
| **Car: 16 MB flash / 8 MB PSRAM (N16R8 shorthand)** | One or two JPEG frame buffers, audio capture, larger tensor arena, local logs, WakeNet plus command recognition, IMU/encoder fusion, low-rate person/obstacle advisory, and a larger application/model partition with OTA headroom. | High-frame-rate YOLO-like perception, guaranteed camera-to-brake latency, or AI as the sole collision stop. Extra PSRAM increases buffering capacity, not compute speed. |

Memory arithmetic explains the boundary: an RGB565 QVGA frame is about 150 KiB and VGA about 600 KiB before additional buffers and conversion workspace. A 32 ms mono 16 kHz int16 audio frame is only 1,024 bytes, so audio buffering is comparatively cheap; WakeNet working memory is documented in the hundreds of KB in [ESP-SR benchmarks](https://docs.espressif.com/projects/esp-sr/en/latest/esp32s3/benchmark/README.html). Exact usable space depends on the module, partition table, camera, IDF version, Wi-Fi/BLE, and enabled components. Validate with `heap_caps_get_free_size`, allocation logs, stack high-water marks, and worst-case control timing on the actual boards.

AI should only publish timestamped advisories such as “slow,” “stop requested,” or “obstacle confidence.” The receiver’s internal watchdog, current/stall guard, and explicit arm/kill policy must decide whether motors are allowed to run. A dropped camera frame must never block the control task.

## Prioritized protocol and control-loop plan

| Priority | Change | Acceptance evidence |
|---|---|---|
| **P0, before faster driving** | Replace receive-callback validation with a bounded preallocated ring/queue containing packet, source MAC, and optional RSSI. Validate, sequence-check, session-transition, and commit state in the receiver task. Keep callbacks to copy/enqueue only. | No callback performs Preferences, PWM/motor calls, serial/display work, or unbounded allocation; measured callback and queue latency under RF load |
| **P0** | Add an independent task watchdog and startup inhibit. Keep motor enable low after boot/reset until initialization, peer/channel setup, and a valid centered safe-start packet complete. Feed the watchdog only from the healthy control task. | Inject blocked task/reset and verify motor output becomes safe; reset reason and maximum loop duration are logged |
| **P0** | Fix first-session persistence, reject session ID zero, and make all new sessions require kill plus centered controls. Define sequence wrap and stale-window behavior explicitly. | Power-cycle, delayed old packet, transmitter reboot, duplicate, stale, wrap, CRC, MAC, and NVS-failure tests |
| **P0** | Make transmitter send completion generation-aware. Once a send transaction expires, ignore its late callback; maintain at most one outstanding frame or associate callbacks with a generation token. | Fault-injected callback delay cannot reopen the send gate or overwrite the status of a newer frame |
| **P1** | Separate transport and application acknowledgements. Telemetry should include highest accepted control sequence, telemetry sequence, command age, session ID, and counters for accepted/duplicate/stale-session/CRC/MAC/send failures. | Dashboard distinguishes MAC success from “receiver acted on N”; loss and recovery graphs are reproducible |
| **P1** | Add encoder feedback and current/stall sensing. Start with wheel-speed estimation, dead-zone calibration, and bounded PI/PID; keep the command watchdog above the loop as the authority. | Report speed step response, tracking error, motor current, stall response, and stop distance |
| **P1** | Add a hardware-level motor enable or emergency-stop path where the board and driver allow it. Keep kill independent of display, telemetry, and AI. | Pull/force the safety input low during maximum command and verify PWM/enable removal |
| **P1** | Build a host-side protocol/fault harness modeled on [airc-telemetry’s testing approach](https://github.com/TeaS0710/airc-telemetry): fuzz frames, test boundaries, simulate loss/reordering, and run sanitizer-backed parsers. | Automated regression covers malformed frames, replay, wrap, timeout, and recovery |
| **P2** | Add IMU fusion and logging, then camera/audio capture behind bounded queues. Use ESP-DSP filters/Kalman and keep AI at a deliberately low rate (start at 1–5 Hz on the car). | Control-loop deadline remains met with logging, camera, and model enabled; dropped observer frames do not affect drive |
| **P2** | Add OTA/model partitions only after measuring flash/cache behavior. Never perform OTA or large flash writes during a drive-critical section. | OTA and filesystem stress test leaves the motor safety path deterministic |

For a 100 Hz link, keep `WIFI_PS_NONE`/sleep disabled unless a deliberately designed wake-window protocol is measured end-to-end. Espressif’s power-saving API requires coordinated station wake windows and connectionless-module intervals ([power-saving guidance](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/api-reference/network/esp_now.html#config-esp-now-power-saving-parameter)). Also verify that both peers remain on channel 6 in deployment; association to an AP on another channel can invalidate the fixed-channel assumption.

## Risks, limitations, and validation gates

The largest risk is false confidence from a successful bench link. ESP-NOW encryption protects the frame but does not solve key extraction, provisioning, counter persistence, or application replay policy. CRC detects corruption and struct/version mistakes; it is not authentication. A firmware-visible token is not a cryptographic improvement, as illustrated by [2A-Trust](https://github.com/OPAMAN123/2A-Trust). If the threat model includes physical firmware extraction, plan key provisioning/rotation or a stronger application-layer design rather than adding ad hoc tokens.

The second risk is timing interference. PSRAM, camera DMA, display SPI, NeoPixel updates, serial logging, Wi-Fi callbacks, and flash writes can create long-tail latency even when average loop time looks good. Measure worst-case—not average—command age, callback duration, queue depth, control-loop duration, and motor stop time. Keep a safety budget with margin, and fail closed when allocation, NVS, peer setup, sensor self-test, or watchdog initialization fails.

The third risk is scope creep in AI. The board can run useful perception and voice features, but published ESP-NN timings do not guarantee a complete low-latency pipeline. Camera inference should slow or stop the car only as an advisory input; independent command age, current/stall, hardware enable, and (where fitted) range sensing must remain authoritative. Board markings, camera sensor, microphone topology, partition table, and exact IDF/Arduino versions were not supplied, so the memory table is a planning bound rather than a certification.

## Conclusion

rc-cyber-truck should differentiate itself by becoming measurable and fail-closed, not by adding another transport or model first. Preserve encrypted ESP-NOW and the existing 120 ms starting policy, isolate callbacks from control state, close the session/callback race cases, and produce reproducible RF, control, and stopping-distance evidence. Then use the S3 car’s extra PSRAM/flash for buffered camera/audio/IMU observers while keeping the remote lean and deterministic. The practical product boundary is clear: the remote commands and monitors, the car controls and protects, and AI may advise but never owns the last word on motor safety.
