# Similar ESP32/ESP32-S3 RC vehicle projects

## Comparative findings

### Takeaway
The closest reusable patterns are (a) ESP-NOW command/feedback with an explicit command timeout, (b) ESP32-S3 Wi-Fi/WebSocket control with a documented watchdog, and (c) a telemetry-first LoRa/IMU stack with unusually strong host-side tests. Most small RC-car repositories do **not** implement closed-loop wheel feedback or publish reproducible vehicle tests; those are opportunities for rc-cyber-truck.

### Concrete radio/failsafe comparison
- **ESP-NOW:** Deejpotter and RawFish69 are the most relevant low-latency peer-to-peer references. Deejpotter’s explicit 1-second command timeout is a useful baseline; RawFish69’s controller/bot return path supports telemetry/visualization but its README does not state a timeout. Sources: [Deejpotter README](https://github.com/Deejpotter/esp32-wireless-car), [RawFish69 README](https://github.com/RawFish69/ESP32-RC-Car).
- **Wi-Fi/WebSocket:** vitorccs demonstrates browser/gamepad control and explicitly stops motors if periodic commands cease. This is convenient for rc-cyber-truck commissioning, but Wi-Fi AP/WebSocket should not be assumed equivalent to a robust long-range RC link. Source: [vitorccs README](https://github.com/vitorccs/esp32s3cam-rc-car).
- **Bluetooth Classic HID:** liangpeng331 keeps the embedded architecture simple but has no published loss-of-control timeout and uses simplified HID parsing. Source: [liangpeng331 README](https://github.com/liangpeng331/esp32-remote-car/tree/esp32-rc-car-initial).
- **LoRa:** airc-telemetry is the only surveyed project with explicit packet-rate/airtime calculations, CRC/link-quality handling, and tested degraded modes. Source: [airc-telemetry README](https://github.com/TeaS0710/airc-telemetry).

## Recommendations, gaps, and method

### Recommendations for rc-cyber-truck
1. Keep a **hard receiver watchdog** independent of the drive loop: timestamp every valid command, command a neutral/brake state on timeout, and require an explicit re-arm after link recovery. Start with a substantially shorter bound than 1 s for a fast vehicle, then measure worst-case radio/UI jitter. This is directly motivated by Deejpotter and vitorccs, not a claim that either is sufficient for racing. Sources: [Deejpotter](https://github.com/Deejpotter/esp32-wireless-car), [vitorccs](https://github.com/vitorccs/esp32s3cam-rc-car).
2. Separate **control radio** from telemetry where practical. ESP-NOW is a good native control baseline; if range and link robustness dominate, borrow airc-telemetry’s packet CRC, sequence numbers, RSSI/link-quality, airtime budget, and explicit degraded-mode policy. Source: [airc-telemetry](https://github.com/TeaS0710/airc-telemetry).
3. Add quadrature encoders and publish actual wheel speed/odometry. Deejpotter shows practical ESP32 encoder pin mapping and PID placeholders, while the other car projects mostly leave encoders absent/optional. Source: [Deejpotter](https://github.com/Deejpotter/esp32-wireless-car).
4. Use an IMU for yaw-rate/slip/jump and diagnostics, but do not substitute it for wheel feedback. RC-VOLT and airc-telemetry provide complementary architectures: MPU6886 over a second node/I2C versus high-rate QMI8658 plus ESKF. Sources: [RC-VOLT](https://github.com/Ian-cmd-ops/ESP32-RC-Telemetry-VOLT), [airc-telemetry](https://github.com/TeaS0710/airc-telemetry).
5. Adopt airc-telemetry’s testing posture: host-side packet/state-machine tests, fuzz malformed frames, simulate sensor/radio failures, test watchdog transitions, and verify logs/telemetry against a deterministic vehicle simulator. Source: [airc-telemetry tests and README](https://github.com/TeaS0710/airc-telemetry).
6. Use the ESP32-S3 WebSocket car only as a commissioning/UI pattern; its browser control, camera and watchdog are useful, but it does not document encoder, IMU, or rigorous control-loop tests. Source: [vitorccs](https://github.com/vitorccs/esp32s3cam-rc-car).

### Gaps and source-quality notes
- Repository star counts above were queried directly with `gh api repos/<owner>/<repo>` on 2026-11-14; stars are snapshot metadata, not a quality ranking. Branches matter: the Bluetooth car is on `esp32-rc-car-initial`, and RC-VOLT is on `BetaReleaseCandidates`.
- README-level evidence cannot prove that every advertised failsafe works under real RF interference. Bench and range tests should be added before treating any design as safety-critical.
- No surveyed repository gives a complete, independently reproducible closed-loop motor-control benchmark (encoder calibration, speed tracking error, latency distribution, or stopping distance). This is a key research gap for rc-cyber-truck.
- Firecrawl was not available in this environment. Research used direct GitHub repository pages/raw content, GitHub CLI API metadata, and the project’s linked primary documentation; no aggregator claims were used as evidence.
